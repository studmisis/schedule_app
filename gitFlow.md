# Git Workflow

## Структура веток

В проекте используется следующая схема работы с ветками:

```text
main
│
└── dev
    │
    └── feature/*
```

---

## Main

`main` — стабильная ветка проекта.

Используется только для проверенного и готового к использованию кода.

Правила:

- прямой push в `main` запрещён;
- изменения попадают только через Pull Request;
- для слияния в `main` необходимо получить минимум 2 Approve от участников команды;
- после одобрения изменения вливаются через Squash Merge.

---

## Dev

`dev` — основная ветка разработки.

Используется для объединения изменений команды и предварительного тестирования.

Правила:

- прямой push в `dev` запрещён;
- изменения попадают только через Pull Request;
- для слияния в `dev` необходимо получить минимум 1 Approve от участника команды;
- после одобрения изменения вливаются через Squash Merge.

---

## Feature branches

Каждая новая задача выполняется в отдельной ветке.

Ветки создаются только от актуального `dev`.

Примеры:

```text
feature/auth
feature/user-profile
feature/calendar
```

---

## Общий процесс работы

### 1. Обновить dev

Перед началом работы необходимо получить последние изменения:

```bash
git checkout dev
git pull origin dev
```

---

### 2. Создать ветку задачи

Создать новую ветку от `dev`:

```bash
git checkout -b feature/task-name
```

Пример:

```bash
git checkout -b feature/auth
```

---

### 3. Выполнить изменения

После завершения работы:

```bash
git add .
git commit -m "Description of changes"
```

---

### 4. Обновить ветку перед Pull Request

Перед отправкой ветки необходимо убедиться, что в ней есть последние изменения из `dev`.

Обновить `dev`:

```bash
git checkout dev
git pull origin dev
```

Вернуться в свою ветку:

```bash
git checkout feature/task-name
```

Обновить ветку:

```bash
git merge dev
```

Если появились конфликты — исправить их и завершить merge.

---

### 5. Отправить ветку на GitHub

```bash
git push -u origin feature/task-name
```

---

### 6. Создать Pull Request

Pull Request создаётся по схеме:

```text
feature/task-name → dev
```

После:

- проверки изменений;
- Code Review;
- получения необходимого количества Approve;

выполняется:

```text
Squash Merge
```

---

## Релиз в Main

Когда изменения готовы и протестированы в `dev`:

Создаётся Pull Request:

```text
dev → main
```

После получения 2 Approve выполняется:

```text
Squash Merge
```

После этого изменения попадают в стабильную ветку `main`.

---

## Общая схема работы

```text
feature/*
     |
     | Pull Request
     ↓
    dev
     |
     | Pull Request
     ↓
   main
```

---

## Основные правила команды

- Не работать напрямую в `main`.
- Не работать напрямую в `dev`.
- Каждая задача выполняется в отдельной ветке.
- Новые ветки создаются только от `dev`.
- Перед созданием Pull Request необходимо обновить свою ветку от актуального `dev`.
- Все изменения проходят через Pull Request.
- Перед Merge обязательно проводится Code Review.
- Для объединения используется Squash Merge.
- `main` содержит только стабильный проверенный код.
